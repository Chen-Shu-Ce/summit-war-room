## 〇、解析中心（進入點）

對應流程圖的前半段：**AI 圖說解析 → 圖說 / 規範 BOQ → WBS → 規格 + QTO → 差異 / 特殊規格 → RFI**。

1. 填專案名稱、選合約型態。
2. 上傳四類文件：**圖說 / 規範 / BOQ / 設備表**。圖說可再標記平面圖／系統圖／詳圖／表單（由檔名預猜）。
3. 勾選分析範圍（全工程或指定大類）。
4. 按「開始解析」，得到九項指標、流程階段列與 RFI 候選清單。

### 九項指標怎麼算出來的

| 指標 | 定義 |
|---|---|
| 圖說完整性 | 五項可查證比例的加權，見下 |
| WBS | 範圍內有工項的分類節點數 |
| 工項 | 範圍內工項數 |
| 材料／設備 | 扣掉「式」計價的統包項 |
| 數量已確認 | 基準判定狀態為 ok（非需複核、非鎖定） |
| 特殊規格 | 工項標記 `special`（無法用標準品替代） |
| 差異 | 圖面量與 BOQ 量差異超過容忍門檻的項數 |
| RFI 未結案 | 候選＋已發出＋已回覆的總數（逾期另計並標紅） |
| 長交期 | 前置期 ≥ `longLeadDays`（預設 90 天） |

**圖說完整性不是 AI 打的分數**，是五個比例的加權，點開可逐項攤開：

| 項目 | 權重 |
|---|--:|
| 工項有數量來源（圖面量或 BOQ 量） | 30% |
| 工項已連結圖面（量測或圖層彙總） | 25% |
| 規格完整（材質／尺寸／等級／標準） | 25% |
| 圖面已設定比例 | 10% |
| 無未解 RFI | 10% |

要拉高它只有一條路：補文件、補規格、設比例、結案 RFI。換演算法不會讓它變好看。
沒有工項時直接回 0 —— 不靠「沒有 RFI」湊分數。

### 六類 RFI 偵測規則

| 類型 | 觸發條件 | 證據 |
|---|---|---|
| 圖說 ≠ BOQ | 差異率超過容忍門檻 | 兩邊數量、差異率、數量出處 |
| 圖說 ≠ 規範 | 工項規格與規範文件同一行的材質／等級 token 無交集 | 規範原文與行號 |
| 平面圖 ≠ 系統圖 | 同一設備標籤在兩類圖的實例數不同 | 各自的標籤清單 |
| 設備表 ≠ 詳圖 | 標籤只出現在設備表或只出現在圖面 | 兩邊出現次數 |
| 數量無法判斷 | 無任何數量來源／未連結圖面／面積取自未封閉輪廓 | 各來源狀態與原因 |
| 規格不完整 | 缺少該類工項的必要規格屬性 | 現有規格與缺少項目 |

兩個刻意的設計，都是為了**不製造假 RFI**（假 RFI 比沒有 RFI 更糟，它讓人開始忽略整張清單）：

- **泛稱不參與衝突判定**。「不鏽鋼」兩邊都會出現，拿它比對會把 `SUS304 vs SUS316` 的真衝突洗掉；
  反過來拿模糊詞宣稱衝突則會製造假案。所以另立一組高特異性 token（SUS3xx、Sch__、IP__、SD___…）。
- **必要規格屬性依工項性質而定**。混凝土的規格就是強度（`f'c=280`），要它填「材質、尺寸」只會生出假 RFI；
  鋼筋要的是等級＋號數＋標準。工項可用 `requiredSpec` 覆寫。

### RFI 狀態流

偵測出來的只是「候選」。要成為閉環，它得走完一整條狀態鏈：

```
候選 ──發出──→ 已發出 ──登記回覆──→ 已回覆 ──結案──→ 已結案
  │                │                              ↑
  └──不追（必填理由）─┴──────────直接結案────────────┘
                                   已結案／不追 ──重開──→ 回到前一狀態
```

三個刻意的設計，少了任何一個這功能就是裝飾品：

**1. 文號在「發出」時才配並凍結。**
偵測階段不給文號 —— 沒發出去的東西不該有正式文號。因為 RFI 是每次重算產生的，
若依排序編號，重算一次順序變了，你已經發文出去的 `RFI-003` 就會變成別人。
發出時才配號、並把**問題內容快照凍結**：之後就算重新解析、條件改變，
你發文問的那句話都不會被悄悄改寫。

**2. 已發出的 RFI 即使條件消失也保留。**
設計單位改了圖，下次偵測就抓不到那筆不一致 —— 但公文已經發出去了。
系統會保留該筆並標記「**條件已消失**」，提醒你確認後結案，而不是靜默刪掉一筆已發出的公文。
候選則相反：條件消失就消失，不留垃圾。

**3. 未結案的 RFI 會擋住該工項轉採購。**
預設擋「高嚴重度」（參數可調為「中以上」或「不擋」）。閘門以**工項**為單位：
同一工項上還有其他未結案的高嚴重度 RFI 就不放行。出路是把它發出並結案，
或填理由「不追」—— 這個摩擦是刻意的，等於強迫你對每一筆問題做出決定。

**結案動作就是閉環本身**：

| 動作 | 效果 |
|---|---|
| 採用回覆數量 | 寫入工項的**人工確認**，簽核人記為回覆人、理由記為 RFI 文號＋回覆原文 |
| 採用回覆規格 | 更新工項規格 |
| 無需變更 | 只留紀錄 |

登記回覆時要求**原文照抄**：結案若採用回覆數量，那段文字會成為工項上的「確認理由」，
是日後估驗與爭議時的依據。改寫過的回覆沒有證據力。

每筆 RFI 都有完整歷程（誰、什麼時候、從什麼狀態到什麼狀態、附註），匯出的 Excel 含
狀態／公文文號／發出日／期限／逾期／回覆內容／回覆人／結案動作／不追理由／條件是否仍存在。

### 這裡的「AI」在哪裡

目前沒有。九項指標與每一筆 RFI 都由**明文規則**從已載入文件的實際內容算出，每一條都附證據
（哪份文件、第幾行、哪個數字），可重現、可稽核。
日後若接上語言模型做語意比對，應該把它當成**第二意見**寫進 evidence，而不是取代這些規則 ——
稽核要的是可重現，不是看起來很聰明。

## 二、數量從哪來（這是整個工具的重點）

六種來源，其中只有四種算「獨立量測」：

| 來源 | 獨立 | 基礎分 | 說明 |
|---|:--:|--:|---|
| 人工確認 | ✕ | 88 | 對其他來源做的判斷，不是新的觀測 |
| **圖面計算式** | ✓ | 82 | 圖上寫的算式（見〈二之二〉）。設計者親手寫下的意圖，且會自我驗算 |
| 圖面量 | ✓ | 78 | 量測或圖層彙總 |
| BOQ 量 | ✓ | 70 | 契約／標單數量 |
| 供應商量 | ✓ | 66 | 廠商回覆 |
| 歷史類比 | ✕ | 52 | 外插，僅供參考 |

**人工確認與歷史類比不納入一致性計算。** 把人工填的數字算進「三來源高度一致」，
等於拿自己的答案幫自己背書（circular corroboration），會讓信心分數系統性灌水。

**圖面計算式算獨立，雖然它和圖面量來自同一張圖。** 因為兩者是不同方法、不同作者、
不同時間：設計者的尺寸相乘 vs 我從線段算出來的面積。相符代表圖上畫的跟標的一致，
不符就是二者必有一錯 —— 那是真正的交叉驗證，不是自我印證。

### 基準判定規則（明文、可重現）

```
R1  有人工確認            → 採人工確認（必須有簽核人與理由）
R2  圖面量與 BOQ 量都有：
      |差異率| ≤ 5%        → 採圖面量，狀態 ok
      5% < |差異率| ≤ 10%  → 採圖面量，狀態「需複核」
      |差異率| > 10%       → 鎖定，不產生建議採購量，強制人工確認
R3  其餘                  → 依 人工 > 計算式 > 圖面 > BOQ > 供應商 > 歷史 取第一個有值者
```

差異率分母是 **BOQ 量**（契約基準），不是兩者平均 —— 你要回答的問題是
「相對於標單，圖面多了多少」，不是「兩個數字差多少」。

手動指定基準時，若差異仍超上限，狀態一樣維持「需複核」；覆寫不能靜默繞過閘門。

### 可信度評分

`基礎分 + min(正分總和, +12) + 負分總和`，夾在 0–100，分級 A ≥85 / B ≥70 / C ≥55 / D <55。

正分封頂、負分不封底，是刻意的：**信心不可能高過來源本身的上限，但證據缺陷可以把它打到地板。**
若不封頂，好項目全部飽和在 100，分數就失去鑑別力。

扣分項包括：PDF 未校正（−20）、校正殘差 >2%（−6）、來源嚴重落差（−22）、
未封閉輪廓求面積（−15）、圖層模糊比對（−5）、圖面涵蓋不完整（−8）、
人工確認無理由（−8）、人工值落在量測區間外（−10 ~ −18）。

點表格上的等級徽章可以攤開每一分的來源。**這是可稽核的啟發式評分，不是統計信賴區間**，
UI 上也是這樣寫的 —— 它回答「證據鏈完不完整」，不保證誤差落在某個範圍。

### 建議採購量

```
建議採購量 = 基準量 × (1 + 損耗率)                    ← 對應人工報表的那一行
下單量     = ceil(建議採購量 ÷ 每訂購單位含量, 包裝倍數)，再套 MOQ
到貨量     = 下單量 × 每訂購單位含量
```

例：基準 1,700 M、損耗 3% → 建議 **1,751 M**；若改成 6 M/支，下單 292 支、到貨 1,752 M。
`ceilTo()` 用相對誤差吸收浮點雜訊，避免 `1700 × 1.03 = 1751.0000000000002` 被多進位一階。

這是**關閉機率模式**時的算法。預設是開啟的，損耗率取自分布的指定分位數 —— 見下一節。

### 損耗率機率化（預設開啟）

單一損耗率係數是慣例不是證據。它把一個機率分布壓成一個數字，然後假裝它沒有變異。
`1,751` 看起來很精確，但它不回答「有多少機率會缺料」。

**第一個發現：慣例值系統性偏低。**

| 工項 | 慣用單點 | 相當於 | 意思 |
|---|--:|--:|---|
| 電纜 | 3% | **P30** | 約 70% 的機率會不夠 |
| 網路線 | 8% | **P35** | 約 65% 的機率會不夠 |
| 風管 | 12% | **P39** | 約 61% 的機率會不夠 |
| 抛光石英磚 | 10% | **P39** | 約 61% 的機率會不夠 |

工具會在分布視窗直接把這句話講出來。沒有這個對照，沒有人會知道舊做法偏在哪裡。

**分布**：預設 **PERT（Beta-PERT）**，另可選三角分布與對數常態。三個參數（樂觀／最可能／悲觀）
現場填得出來，也是 PMI／AACE 三點估計的標準做法。

**服務水準是決策不是計算。** 預設 P80，可逐項調整；系統會依缺料代價建議：

| 情境 | 建議 |
|---|---|
| 特殊規格或前置期 ≥180 天 | P95 —— 缺料等於停工數月 |
| 前置期 ≥90 天 | P90 —— 補料來不及 |
| 前置期 ≥30 天 | P85 |
| 短交期料 | P80 —— 缺了可以補 |

**做錯的蒙地卡羅比不做更危險**，它會給你看起來很科學的錯數字。本模組刻意處理五件事：

| # | 陷阱 | 處理 |
|---|---|---|
| 1 | 各項損耗當成獨立 → 大數法則抹平變異，**整包 P80 嚴重低估** | 高斯 copula 單因子模型注入相關係數 ρ（預設 0.3），並同時列出 ρ=0／ρ=設定／ρ=1 讓你看差多少 |
| 2 | 各項 P80 直接相加 → 除非完全相關，否則**高估** | 兩個數字都算出來，差額標為「分散效益」 |
| 3 | 每次跑結果都跳 → 採購數字沒人敢簽 | 固定種子的 mulberry32 PRNG，同輸入必得同輸出 |
| 4 | 對計數類也跑分布 | 只有材料類（長度／面積／體積／重量）模擬；6 台配電盤不會「損耗 0.3 台」 |
| 5 | 先套包裝進位再抽樣 | 在「需求量」層抽樣，再套包裝倍數／MOQ 這些確定性階梯函數 |

**效能**：PERT 的反函數要跑二分法＋連分數，放進 30 萬次抽樣迴圈會慢到不能用。
改成先建 1,024 點分位數查表再線性內插，誤差可忽略而速度與三角分布相同。

**收斂**：回報前後半樣本的 P80 差異，超過 2% 就提示提高迭代次數 ——
不宣稱精確，而是把精確度本身量化出來。

**區間從哪來**：目前是**業界慣例值，不是貴司實證資料**，工具裡也是這樣標示的。
累積 5 筆以上「理論量 vs 實際領用量」即可用 `calibrateFromHistory()` 以實績 P5／P50／P95 取代。
少於 5 筆會拒絕估計 —— 寧可繼續用慣例值並註明，也不要用 3 筆資料假裝有統計基礎。

## 二之二、圖面計算式（第五條數量來源）

台灣 QS 習慣把算式直接寫在圖上：

```
ⓑ 走廊   1.45*3.525+1.8*2.60=9.79m2
ⓚ 大廳   24.565*20.80-62.33-40.39-11.22=397.01m2      ← 算式上方標註 ⓗ ⓘ ⓙ
合計     46.53+9.79+…+397.01=720.96m2
         720.96+788.08=1509.04m2
```

這是**設計者親手寫下的數量意圖**，而且是唯一一條會自我驗算的來源：
算式可以重算、交叉參照可以追、合計可以驗。**不需要任何幾何就能抓出錯**。

因此 `calc` 在基準優先序上排在圖面量測**之前**：
設計者寫下的數字，證據位階高於我對同一張圖的幾何再詮釋
（幾何量要經過比例、圖層、封閉性一堆會出錯的環節）。

### 三條不能違背的規則

| # | 規則 | 為什麼 |
|:--:|---|---|
| 1 | **絕不用 `eval` / `Function`** | 算式來自外部檔案。自己寫詞法分析與遞迴下降求值，`constructor`、`process.exit(1)`、`1;alert(1)` 一律當作語法錯誤拒絕。 |
| 2 | **絕不改圖上的數字** | 算出來不一樣就把兩個都列出來讓工程師判，不「順手修正」。 |
| 3 | **絕不把合理寫法當成錯誤** | 大面積扣除法、階層合計都是正確做法。誤報比不報更糟 —— 沒人會再相信第二次警告。 |

### 驗算的五件事

**1. 算式本身。** 重算並與圖上寫的數字比對。
容差取圖上寫的小數位數：`1.45*3.525+1.8*2.60 = 9.79125`，圖上寫 `9.79` 是四捨五入不是錯誤。
硬要求完全相等，會把一張全對的表判成全錯。

**2. 交叉參照。** ⓚ 的算式上方標著 ⓗ ⓘ ⓙ，代表扣掉的 62.33／40.39／11.22 來自那三列。
逐一比對 —— 圖改版後 ⓗ 變了而 ⓚ 沒同步，就是這裡抓出來的。

**3. 合計。** 每個加項都要對得到某一列的結果。對不到就是孤項，可能漏列也可能重複。
比對池**含其他合計列**，因為總計加小計是正常的階層寫法。

**4. 宣告值。** 圖上常在標題、圖例、統計框各寫一次總面積。
改版時最容易漏改其中一處，而那正是這種表最常見也最貴的錯誤。

**5. 單位一致性。** 同一張表出現 M2 與 M 就要提出來。

### 刻意不當成錯誤的兩種寫法

**大面積扣除法。** ⓚ 扣掉 ⓗⓘⓙ，合計又把 ⓗⓘⓙ 各自加回 —— 這**不是**重複計算：
ⓚ 是挖掉那三塊之後的剩餘面積，加回去才是毛面積。工具只驗「每個加項都有出處」，
不去質疑人家的算法。

**階層合計。** `720.96+788.08=1509.04` 的兩個加項都是小計不是明細列。正常。

### 中文亂碼：讀得出算式，讀不出名稱

中文 DWG 常因缺 SHX 大字型，把中文全部變成 `?`。範例圖 44 個文字有 17 個是亂碼。

**數字與運算子不受字型影響**，所以算式照樣完整解析與驗算。
但工項名稱必須人工對照 —— 工具會明說這件事，不讓人以為它「讀懂了」那些名稱：

> 我讀得出 `8.58*7.265=62.33`，讀不出它叫什麼。

### 與幾何量的交叉比對

計算式與幾何量測**都來自同一張圖，但方法不同、作者不同、時間不同**：
一邊是設計者的尺寸相乘，一邊是我從線段算出來的面積。

- 相符 → 圖上畫的跟標的一致。這是真正的交叉驗證，因此 `calc` 列入獨立來源。
- 不符 → 二者必有一錯：不是標註尺寸過期，就是圖面沒照標註畫。
  差異超過容忍值會產生 **`calc-vs-drawing`** RFI；算式本身有誤則產生 **`calc-error`** RFI。

### 套用時不代為換算單位

計算式單位是 M2、工項單位是 M，工具**擋下來並說明**，不自動換算。
面積換長度需要厚度或寬度 —— 那是工程判斷，不是算術。

### 基準案例：使用者提供的真實計算式表

14 道算式（ⓐ–ⓛ 各列、兩道合計、總計），逐式重算：

| | |
|---|---|
| 重算相符 | **14 / 14** |
| 嚴重問題 | **0** |
| 警告 | 2 —— 皆指向同一件事：ⓐ 列被裁切，`46.53` 沒有出處、ⓛ 參照的 `a` 找不到 |
| 總計 | 1,509.04 M2（圖上另有 2 處宣告相符） |

這張表做得很嚴謹，所以它是最好的**誤報基準**：解析器在它身上一個誤報都不能有。
注入錯誤的回歸測試則確認它真的抓得到：算錯、參照過期、合計漏項、宣告值不符、算式看不懂，五類全部覆蓋。

## 二之三、那一整排 ????：不是缺字型，是我的解碼器選錯了

這是本工具修過**成因最容易被誤判**的一個問題。

畫面上一整排問號，直覺會說「缺中文字型」。但那有兩種完全不同的成因：

| 現象 | 成因 | 位元組還在嗎 | 處方 |
|---|---|:--:|---|
| CAD 顯示 `?` 或方框 | 找不到 SHX 大字型檔（`hztxt.shx`、`gbcbig.shx`…），畫不出字形 | **在** | 補字型檔 |
| 解析工具顯示 `?` / `�` | **解碼器選錯編碼**，位元組被錯誤詮釋 | **不在了** | 換解碼器 |

本工具原本寫死：

```js
new TextDecoder('utf-8', { fatal: false }).decode(buf)   // ← 這一行毀掉所有 Big5 圖
```

台灣的 DXF 幾乎都是 **Big5**（`$DWGCODEPAGE = ANSI_950`），大陸多半是 **GBK**（ANSI_936）。
把它們當 UTF-8 解，每個中文字都變成 U+FFFD —— 字**真的不存在了**，補字型也救不回來。

### 判斷順序

```
0. 整個檔案都是 ASCII        → 沒有什麼好判的，不跳警告嚇人
1. $ACADVER ≥ AC1021（R2007）→ 一律 UTF-8，$DWGCODEPAGE 不作數
2. $DWGCODEPAGE 宣告的編碼    → 但必須跟其他候選比過分數才採信
3. 都不行                    → 評分挑最好的，並明白回報「這是推測的」
```

### 兩個不直覺但關鍵的細節

**一、「零個替代字元」不等於解對了。**
`windows-1252` 是單位元組編碼，幾乎每個位元組都對應得到字。
拿它解 Big5 內容會得到 `¤¤¤å` 這種垃圾，**卻一個 U+FFFD 都不會產生**。
所以檔頭宣告 ANSI_1252 時不能因為「沒有替代字元」就採信 —— 宣告必須接受挑戰。
（轉檔工具改了內容卻沒改檔頭是常態。）

**二、評分要獎勵「連續漢字」，不是漢字總數。**
真實中文詞彙至少兩個字連著；解碼錯誤產生的是散落的孤字。
只數漢字總數的話，用 Shift-JIS 解 Big5 會得到一堆半形片假名夾雜孤立漢字，**分數反而爆高**。

兩種誤解各有指紋，各自重扣：

| 指紋 | 意思 |
|---|---|
| 半形片假名連串（U+FF61–U+FF9F） | 把中文當日文解 |
| 高位拉丁字連串（U+00A0–U+00FF） | 把雙位元組當單位元組解 |
| U+FFFD／C1 控制碼 | 根本解不出來 |

實測分數（內容是 Big5、檔頭謊稱 ANSI_1252 的檔案）：

| 候選 | 分數 | 連續漢字 | 片假名 | 高位拉丁 | 替代字元 |
|---|--:|--:|--:|--:|--:|
| **big5** | **318** | 50 | 0 | 0 | 0 |
| gbk | 84 | 18 | 0 | 0 | 0 |
| shift_jis | −215 | 0 | 30 | 0 | 3 |
| windows-1252 | −255 | 0 | 0 | 51 | **0** |
| utf-8 | −1428 | 0 | 0 | 0 | 119 |

### MTEXT 排版碼

AutoCAD 把字型、字高、寬度、堆疊分數都混在文字內容裡：

```
{\fMSungGBK|b0|i0|c136|p2;\H1.2x;鋼筋混凝土樓版 t=15cm}   →   鋼筋混凝土樓版 t=15cm
\U+4E2D\U+6587  →  中文        %%c100 %%d45 %%p5  →  Ø100 °45 ±5
```

不剝掉的話，工項名稱會混進一堆 `\f...|b0|i0` 的雜訊。跳脫過的 `\{` `\}` 要保留。

### Big5 沒有圈號字元

`ⓐ ① ㈠ Ⓐ` **全部不在 Big5 字集裡**。所以台灣的計算式表實務上用：

- **全形括號** `（a）（b）` —— Big5 有 `（）`
- **圈圈畫成 CIRCLE 幾何、圈裡放一個裸字母** —— 文字層只會看到一個 `a`

兩種都要認得，否則列號與交叉參照全部斷掉。面積單位同理常用 Big5 有的 `㎡`。

### 修好之後才解鎖的事

名稱可讀，才談得上把計算式的列對到 BOM 工項。這在編碼修好之前**做不到** ——
名稱全是問號的時候無從比對。

但比對出來的一律是**建議**，附分數與換算結果，由人確認後才寫入。
而且範例圖的結論是「一個都對不上」，那是正確答案：
**計算式表列的是「空間」（玄關、會議室），BOM 列的是「材料」（電纜、鋼筋），本來就不是一對一。**
樓地板面積要先乘上單位用量才會變成材料數量，那一步是工程判斷，工具不替使用者做。

## 二之四、單位換算：同維度自動，跨維度絕不

原則一條：**同維度自動換算，跨維度絕不自動換算。**

| 換算 | 處理 |
|---|---|
| M² → 坪、CM → M、KG → 公噸 | **自動**，係數固定，並把換算方式寫進數量出處 |
| M² → M | **問工程要寬度**。面積除以寬度才是長度，那個寬度不在算式裡 |
| M² → M³ | **問工程要厚度** |
| 只 → 組 | **不換**。一組含幾只是規格問題，不是單位問題 |
| M² → 樘 | **不換**。一樘門幾 M² 要看門的尺寸，也是規格問題 |
| KG → M | **不換**。單位重隨材質而異，沒有通用係數 |

跨維度時工具會問，不會猜；補進去的寬度／厚度會記在數量出處裡，日後可稽核。

台制單位採法定換算值：

```
1 台尺 = 10/33 公尺                        （經濟部標準檢驗局）
1 坪   = 6 台尺 × 6 台尺 = (60/33)² ≈ 3.3057851 ㎡
```

## 二之五、四捨五入：進位後要求完全相等

圖上寫 `1.45*3.525+1.8*2.60=9.79`，重算是 `9.79125`。**這不是錯誤，是只取小數點後兩位。**

比對方式因此是：**把重算值四捨五入到圖上的位數，然後要求完全相等。**
進位過後再給一個容差，等於同一件事放寬兩次 —— 那會讓真的算錯溜過去。

兩個實作細節：

**一、先修二進位表示誤差再進位。**
`3.45*3.90` 在浮點裡是 `13.454999999999998`，直接 `*100` 再 `Math.round` 會得到 **13.45**，
但工程上 `13.455` 四捨五入就是 **13.46**。先 `toPrecision(15)` 把表示誤差抹掉才進位。

**二、比整數，不比浮點。** 兩邊都進位到同一個小數位後，比較 `round(a×10ⁿ) === round(b×10ⁿ)`。

結果：進位後只差一個最小位就判定不符。圖上寫 `62.34` 而重算是 `62.33` → **算錯**，
且錯誤訊息同時列出重算值、圖上值、以及未進位前的原值，不代為修正。

## 二之六、一張真實地籍圖教會的事

前面所有的 fixture 都是自己造的。第一次拿到真檔案（AutoCAD 2018 DWG，地籍暨建築線套繪圖，
95 KB，經 LibreDWG 轉成 409 KB DXF）就冒出**三個自己造測資永遠想不到的問題**。

### 一、轉檔器宣告的編碼是錯的，而我的規則剛好擋下來

```
$ACADVER      = AC1032        （AutoCAD 2018）
$DWGCODEPAGE  = ANSI_950      （Big5）
實際內容       = UTF-8
```

LibreDWG 寫出 UTF-8 內容，卻照抄了原 DWG 的 Big5 codepage 宣告。
「R2007 以後一律 UTF-8、不看 `$DWGCODEPAGE`」這條規則因此救了這張圖 ——
乖乖相信檔頭的實作會把 `L - 建築線` 解成亂碼。

中文圖層名完整讀出：`L - 建築線`、`L - 地界線`、`T - 地籍`、`PDF_幾何圖形`、`PDF_文字`。
（`PDF_*` 圖層說明這張圖是從 PDF 匯入向量化來的，不是原生 CAD 繪製。）

### 二、`$INSUNITS` 說公厘，座標卻是公尺 —— 差一千倍

這是最危險的一個，因為**畫面上完全看不出來**：整張圖等比例縮小，線條該在哪還在哪。

```
$INSUNITS = 4（公厘）
實際座標  = E 260,384–260,602 ／ N 2,737,396–2,737,603
```

那是 **TWD97 TM2（二度分帶，EPSG:3826）**，而這個座標系的單位**依定義就是公尺**。
圖上自己畫的格網標註 `E260400` / `N2737400` 獨立佐證了這件事。

代價很具體：

| 圖層 | 依 `$INSUNITS` 宣告 | 實際 |
|---|--:|--:|
| L - 建築線 | 0.3630 M | **363.05 M** |
| L - 地界線 | 0.4000 M | **399.97 M** |
| NE_GRID（格網） | 1.2000 M | **1200.0 M** |

格網剛好 1200 M（6 條 × 200 M）與 217.7 × 207.0 M 的地塊大小互相印證 ——
公尺才是對的。若照宣告走，這個一千倍的錯誤會一路安靜地流進採購包、請購單、ERP。

因此新增 `survey.js`：**把宣告的單位套上去，看圖變成多大**。
一張營建圖的內容跨距若算出來是 0.22 公尺或 2,700 公里，那不是圖有問題，是宣告有問題。

- TM2 座標範圍內 → 單位依定義是公尺，宣告不是公尺就是錯的。
- 非 TM2 → 檢查跨距是否落在 0.5–20,000 公尺，並找出能讓它落回合理範圍的單位。
- **只回報，不自動改。** 改單位會改變每一筆數量，那是工程判斷。改過會留下可稽核紀錄。

### 三、座標分成兩群，自動全覽因此完全失效

```
1,411 點  在 TM2 座標上        → 地籍內容，實際 217.7 × 207.0 M
  655 點  在原點旁 ±30         → 圖例表、指北針、圖框
```

對全部實體取外框得到 **260,651 單位**的跨距。自動全覽照這個縮放，
整張圖縮成畫面上兩個看不見的點 —— 工具實際上不能用。

`contentBounds()` 依座標空隙分群、取主群。但**排除點是有代價的判斷，不能靜默做掉**，
所以加了兩道門檻：

| 門檻 | 值 | 為什麼 |
|---|--:|---|
| 主群佔比 | ≥ 60% | 五五分的兩群不是離群，是圖上真的有兩塊東西 |
| 範圍縮減 | ≥ 90% | 縮不了多少就代表本來就是一整塊，不該切 |

真實圖：主群佔 **68%**、範圍縮 **99.99%** → 排除離群點，全覽正常。
兩群勢均力敵時（50/50）**一個點都不排除**，改成回報「分不出主體，請自行確認要量哪一塊」——
安靜丟掉一半的圖，比範圍太大危險得多。

這道門檻是被一個誤報逼出來的：第一版把一個 10 單位寬的矩形切成兩群，
因為重複的 Y 值讓「中位空隙」變成 0，門檻整個塌掉。中位空隙必須算在**相異值**上。

### 四、地號不是減法

這張圖有 117 個相異文字，其中一大半是地號：`1267`、`2-13`、`1006-2`、`2-35`…

`2-13` 對一個算式解析器是地雷。實測結果：**計算式偵測器一列都沒抓，零誤報**。
因為 `parseExpression` 要求必須有 `=`，而地號沒有。這張圖本來就沒有計算式表，
正確答案就是「沒有」。

### 沒能驗證的部分

- **DWG 直讀仍然做不到。** 這次是在開發環境自行編譯 LibreDWG 轉檔後才讀得到。
  正式環境走的是 `tools/dwg-converter/` 的內網服務，架構相同但**沒有用這張圖實測過**。
- **這是一張地籍圖，不是施工圖。** 它驗證了編碼、單位、座標、誤報這四件事，
  但沒有驗證計算式表、圖層抓量對應工項、數量比對 —— 那些還是只有自造測資撐著。

## 二之七、一張真實施工圖教會的事

第二張真檔案：**φ60cm 基樁詳圖**（A1、PDF 1.6、凃秀瑋建築師事務所、芎林鄉新設資源回收貯存場新建工程）。
它同時給了一個好消息與一個**會讓數量錯十倍的壞消息**。

### 好消息：圖框的比例讀得出來

pdf.js 只抽得到 **5 條文字** —— 圖上所有尺寸標註（600、120、28-7φ、#3@150）
都被轉成曲線，程式讀不到。但那 5 條裡剛好有圖框的比例欄：

```
"芎林鄉新設資源回收貯存場新建工程"   "A3圖:1:200"   "A1圖:1:100"   "比例"   "凃秀瑋建築師事務所"
```

而頁面是 **2384 × 1684 pt = 841.0 × 594.1 mm**，誤差 **0.08 mm** 精確吻合 A1。

這兩件事湊起來就能算出比例，省掉一次校正。而且紙張吻合得這麼精確，
**本身就是「這份 PDF 沒有被縮放過」的證據** —— 被「符合頁面大小」列印過的檔案不會這麼準。

`pdfscale.js` 因此做三件事：判紙張規格、找比例宣告、依實際紙張挑對的那一個。
同一張圖同時標 A1 與 A3 兩種比例是常態，**挑錯就差一倍**；
紙張對不上圖框標的（例如 A1 圖輸出成 A2）就拒絕判定，要求改用兩點校正。

### 壞消息：一張圖不只一個比例

圖框寫 `A1圖:1:100`。但 SECTION A-A 的 `600` 尺寸線，實測在紙上是 **59.97 mm**：

```
600 mm ÷ 59.97 mm = 1 : 10.00
```

**那一區是 1:10，跟圖框差十倍。**

這是營建圖的常態 —— 平面 1:100、大樣 1:10/1:20/1:50 —— 卻讓「讀圖框比例自動套用」
這個功能從省事變成危險：整張套 1:100，每一個大樣的量測都會大十倍，
**而且畫面上完全正常，沒有任何跡象**。跟 DWG 那個 `$INSUNITS` 是同一類錯誤。

### 因此：比例分區

`viewer.js` 改成支援**分區比例**。校正時可以選「只套用在這一區」，
以校正的兩點為中心建立一個矩形分區；之後落在該區內的量測自動用該區比例，區外用整頁比例。

實測驗證（同一條 170.08 pt 的線）：

| 量法 | 結果 | 圖上標註 |
|---|--:|--:|
| 整頁套圖框 1:100 | **5.997 M** ✗ | 0.6 M |
| 該區建 1:10 分區 | **0.600 M** ✓ | 0.6 M |
| 分區外同樣長度 | 5.997 M ✓ | （維持整頁比例）|

兩個配套的設計決定：

- **比例對話框最前面就警告**「一張施工圖通常不只一個比例」，而不是把它藏在說明裡。
  讀得到圖框比例是方便，不是授權整張套用。
- **整頁還沒有比例時，第一次校正先定整頁**。只建分區會讓分區以外的圖全部量不出數字 ——
  那比套錯比例更沒用。第二次以後才預設「只套用在這一區」。

### 沒能驗證的部分

- **尺寸標註讀不到。** 這張圖的 600、120、#3@150 全是曲線，工具無法自動讀值校正，
  仍需人眼看標註、手動輸入。要自動化只能上 OCR，而 OCR 讀錯一個字就是錯一個數量級。
- **分區範圍是猜的。** 目前以校正兩點為中心外擴 1.5 倍。真實視圖的邊界工具並不知道，
  外擴太大會蓋到隔壁視圖。正確做法是讓使用者框選視圖範圍，這還沒做。
- **這張圖沒有工程數量。** 它是一張詳圖，驗證了比例判讀與分區機制，
  但「圖層抓量對應工項」「多來源數量比對」仍然只有自造測資撐著。

## 二之八、一份掃描標單圖教會的事：有些圖本來就不能量

第三張真檔案：**空軍第二戰術戰鬥機聯隊「410營舍鋼棚整修工程」**，7 張 A3、18 MB。
它推翻的不是某個功能，而是一個更根本的假設：**工具預設「載得進來就能算」。**

### 這份檔案的三個性質，每一個都是致命的

**一、純掃描。** 七頁的繪圖指令完全相同：

```
{ transform: 2, save: 1, dependency: 1, paintImageXObject: 1, restore: 1 }
```

整頁就是**一張點陣圖**。零文字、零向量、零字型。所以：
讀不到圖框、讀不到比例、讀不到任何尺寸標註、沒有端點可吸附、沒有圖層可彙總。

**二、圖框寫著 `NO SCALE`。** 七張標題欄的比例尺欄位全部如此，單位欄寫 `CM`。

而第一版的 NTS 偵測**沒有收 `NO SCALE`** —— 只認 `NTS`、`N.T.S.`、`不按比例`、`無比例`。
偏偏 `NO SCALE` 才是台灣標單圖上最常見的寫法。這是個實打實的漏洞。

**三、圖說自己聲明尺寸僅供參考。** 施工需知白紙黑字：

> 3、圖說標註之尺寸**僅供參考**，施工前承商須至現場丈量精確尺寸，經監造單位核准後方可配合現場實際尺寸施作。
> 4、本案為**總價承攬**工程……承商不得異議。
> 5、本工程圖說尺寸、規範如未特別註明允許誤差，誤差值以 **5%** 為驗收基準。

（第 5 條的 5% 與貴司給的容忍值完全相同，是個有意思的印證。）

### 「未校正」與「不按比例」是完全不同的兩件事

這是這一節的核心，而工具原本把它們混為一談：

| | 意思 | 處方 |
|---|---|---|
| **未校正** | 缺一個數字 | 點兩點、輸入已知長度，就能算 |
| **不按比例** | **圖本身的幾何就不代表實際尺寸** | 校正再準也沒有意義；圖上寫的數字才算數 |

所以 `viewer` 新增 `setNotToScale()`：一旦標記，**不論有沒有校正、不論校得多準，
`engValue()` 一律不給工程單位**。實測：硬套 `setDeclaredScale(100)` 之後量 200 pt，
回傳仍是 `{ value: null, notToScale: true }`。量測標籤顯示「不按比例」，比例晶片顯示
「不按比例（量測無意義）」。

給了工程單位，就等於替一個沒有意義的數字背書。

### 讀不到 ≠ 沒有

純掃描頁讀不到文字，所以**圖框上就算寫著 NO SCALE 也抓不到**。
工具不能因此當作「沒有 NTS 標示」—— 那是把「我看不到」當成「它不存在」。

因此掃描頁會明白說：

> 因為讀不到文字，圖框上就算寫了比例也抓不到。請人眼確認標題欄的比例尺欄位 ——
> 台灣的標單圖很常寫「NO SCALE」，那種圖**不能量**，尺寸只能照圖上寫的數字讀。

並提供一個勾選格讓人確認。**這是工具問不到、只能問人的事，所以它就問。**

### 那這張圖到底還能不能用？

能，但走的是完全不同的路。圖上的**尺寸數字是完整的**：

| 來源 | 內容 |
|---|---|
| A02 柱位圖 | 2160（425+245+400+600+490）× 1555、1880 × 1880；柱 H150×150×7×10；副架 C125×50×20×2.6 **@60cm**；新設柱高 180cm |
| A05 大樣圖 | 跨距 1880、斜邊 965 + 915；H350×250×9×14；基座鋼板 PL410×400×12；高拉力螺栓 φ16 |

這些數字要**用讀的，不是用量的**。讀完填進工項的「人工確認」欄，並註明出自哪一張圖 ——
數量的出處才是對的：它來自圖上的標註，不是來自工具對一張示意圖的量測。

**而工具的其餘部分完全不受影響**：損耗率機率化、採購包拆包、施工工序反推送審發包日、
原料行情連動 —— 這些吃的是「數量」，不在乎數量是量出來的還是讀出來的，
只在乎**出處標對了沒有**。

### 三張真檔案的共同結論

| 檔案 | 宣告 | 實際 | 錯多少 |
|---|---|---|--:|
| 地籍圖 DWG | `$INSUNITS` = 公厘 | 座標是公尺 | **1000 倍** |
| 基樁詳圖 PDF | 圖框 1:100 | 大樣是 1:10 | **10 倍** |
| 標單圖 PDF | （掃描，讀不到） | `NO SCALE`，尺寸僅供參考 | **無法量測** |

三張圖、三個不同的錯誤，**共同點只有一個：宣告與現實不符，而且都安靜地錯。**
畫面上永遠看起來正常。

這也是這個工具做這麼多「檢查」的理由 —— 算量工具真正的風險從來不是算錯，
是**在一個錯誤的前提上算得很精確**。

## 三、圖面怎麼讀

### DXF（原生支援）

自寫的 ASCII DXF 解析器，支援 LINE / LWPOLYLINE（含 bulge 弧）/ POLYLINE+VERTEX /
CIRCLE / ARC / ELLIPSE / SOLID / 3DFACE / TEXT / MTEXT / INSERT（圖塊遞迴展開、含矩形陣列）/ DIMENSION。

- bulge 弧長：`θ = 4·atan(|b|)`，`R = c / (2·sin(θ/2))`，`L = R·θ`；面積另加弓形修正。
- 單位取 `$INSUNITS`；未定義時強制使用者指定，不猜。
- SPLINE 以控制點折線近似（長度為下界並標記），HATCH 只計數不算面積 —— 寧可少算也不要假裝算得出來。
- 圖層彙總（總長／總面積／實體數／圖塊數）可一鍵對映到工項，靠 `layerHints` 自動猜。

### PDF（原生支援）

pdf.js 渲染 + 像素邊緣吸附（向量與掃描件都適用）。**未校正比例前不顯示任何工程單位。**

- 兩點校正：點兩點已知尺寸、輸入實際長度。
- 多段校正：累積 2 段以上改用最小平方求比例，回報 **RMS 殘差** —— 這是「這份圖量得準不準」的客觀證據，直接餵進可信度。
- 圖框比例（1:N）：`metersPerPt = (0.0254/72) × N`。此法假設 PDF 由 CAD 以 1:1 圖紙尺寸輸出且列印未縮放，
  實務常見「A1 縮印 A3」而失真，所以評分上扣分。

### WBS 編碼

採貴司自有的九大類：

```
100 土建   200 裝修   300 電氣   400 給排水   500 消防
600 空調   700 弱電   800 設備   900 其他
```

三層結構：**大類（3 位）→ 中類（3 位）→ 小類（3 位，選用）→ 工項**。例如
`300 電氣 → 320 幹線 → 321 電纜 → 321.01 低壓電力電纜 XLPE`。
範本在 `public/data/wbs-template.json`，直接改成貴司標準即可，程式不綁任何特定編碼。

### DWG（需轉檔，這是硬限制）

DWG 是 Autodesk 的封閉二進位格式。本專案**不內嵌任何 DWG 解析器**，原因是授權而非技術：
唯一可靠的自由實作 GNU LibreDWG 是 **GPL-3**，把它連結進網站程式會讓整份程式落入 GPL-3 散布義務。
改成呼叫獨立行程／獨立服務則不會。

**選項 A（採用中）：自建轉檔服務，圖面不出公司**

本專案已附上可直接跑的實作：`tools/dwg-converter/`（零相依 Node 服務 + Dockerfile + 測試）。

```bash
docker build -t dwg-converter tools/dwg-converter
docker run -d -p 8787:8787 -e TOKEN=your-secret dwg-converter
# 網站端：DWG_CONVERT_URL=http://<內網位址>:8787  DWG_CONVERT_TOKEN=your-secret
```

轉檔器解析順序：`DWG_CONVERT_CMD` → `ODAFileConverter` → `dwg2dxf`。細節見該目錄的 README。


```bash
# ODA File Converter（Open Design Alliance 免費工具，品質最穩）
ODAFileConverter /in /out ACAD2018 DXF 0 1 "*.dwg"

# 或 LibreDWG（GPL-3，命令列獨立行程）
dwg2dxf -o out.dxf in.dwg
```

把它包成一支 HTTP 服務，契約很單純：

```
POST /                       ← DWG_CONVERT_URL 指向這裡
Content-Type: application/octet-stream
X-Filename: <URL 編碼的原始檔名>
Body: DWG 原始位元組

200 OK
Content-Type: application/dxf
Body: ASCII DXF 文字（必須以 `0 / SECTION` 開頭）
```

然後設定：

| 環境變數 | 用途 |
|---|---|
| `DWG_CONVERT_URL` | 轉檔服務端點（未設定時 `/api/convert-dwg` 回 501 並附指引） |
| `DWG_CONVERT_TOKEN` | 選用，帶 Bearer 認證 |
| `DWG_CONVERT_TIMEOUT_MS` | 預設 120000 |
| `DWG_MAX_BYTES` | 預設 40 MB |

`/api/convert-dwg` 會驗證回應確實是 ASCII DXF（開頭必須是 `0 / SECTION`），不是就回 502，
不讓前端拿垃圾去硬解析。

**選項 B：瀏覽器端 GPL WASM（自負授權責任）**

頁面載入前設定 `window.TAKEOFF_LIBREDWG_BASE = 'https://…/libredwg-web/'`，
會動態載入 `@mlightcad/libredwg-web`（GPL-3、WASM 約 10 MB）並用 `dxf.js` 的 `fromDwgDatabase()` 轉成內部模型。
**本專案不散布這份程式碼**，開關預設關閉，商用前請先做授權合規判斷。

**選項 C：人工轉出** — 另存 ASCII DXF 或列印向量 PDF。功能完全相同，五秒的事。

## 四之二、基準版（Baseline）與請購單（PR）

對應流程圖末段：**採購需求/Package → 工程確認 → Baseline/PR → 正式發包**。

### 凍結

採購包按「凍結為基準版」，把當下每個工項的採購狀態壓成快照：
規格、單位、採購基準、基準量、損耗率、建議採購量、下單量、到貨量、單價、金額、可信度、前置期。

**必須填工程確認人** —— 沒人確認的快照不是基準版，只是一份沒人負責的檔案。
這一欄就是流程圖上 Package 與 Baseline 之間的那一關。

重新凍結產生新版（rev 2、rev 3…），每版記錄誰確認、何時、為什麼，並指向前一版。

### 凍結不等於鎖住

**Baseline 的用途不是禁止改動，而是讓「改了什麼、誰改的、差多少錢」無所遁形。**
凍結後資料照樣能改，但每一項異動都會被對照出來：

- 基準版卡片顯示「較本基準版有 N 項異動…金額差 X」
- 工程量清單上，異動過的工項下方直接標出 `較 BL-PKG-001-01 異動：基準量 +60、建議採購量 +61.80…`
- 點「變更」看完整對照表：每個欄位的基準版值、現值、差異

浮點雜訊（`1751` vs `1751.0000000000002`）不會被當成變更 —— 相對誤差 1e-9 內視為相同。

### 請購單編號

樣板可設定，預設 `PR-{YYYY}{MM}{DD}{SEQ:4}` → **PR-202609130001**。
可用 token：`{YYYY} {YY} {MM} {DD} {SEQ:n}`。

**流水號的重置範圍由樣板自動推導**：有 `{DD}` 就每日重置、只有 `{MM}` 就每月重置、
只有 `{YYYY}` 就每年重置。這是為了避免「編碼精確到日、流水號卻全年連續」這種自相矛盾
（也可明確覆寫）。其他區間的舊號不會干擾本區間的取號。

### 單價換算

PR 明細的單價是以**訂購單位**計價，不是材料單位。
6 M/支的管子，單價寫的是「每支」= 每公尺 × 6 —— 否則 ERP 那邊金額會差六倍。

### 進 ERP

本工具**不綁任何一套 ERP**：中性資料模型 + 可設定的欄位對映。

| 項目 | 說明 |
|---|---|
| 結構 | 表頭 + 明細兩層，對應多數 ERP 的請購單 |
| 檔案格式 | 兩檔式（header.csv + detail.csv，明細帶單號可對回表頭）或單檔式（表頭欄位攤進每一列） |
| 欄位對映 | 把對方 ERP 匯入範本的欄名（`PURCH_NO`、`ITEM_NO`…）填進對映表，匯出的表頭就用那個名字 |
| 料號把關 | 缺 ERP 料號的項目**先擋下來**並提供就地補填 —— 沒有料號送進 ERP 一定退件，不該等到 ERP 前台才發現 |

## 四之三、施工工序（Sequence）

採購日期不該從前置期猜。它應該從**施工需求**反推出來。這一節是整條鏈的最後一段：

```
圖說 → WBS → BOM → 工序 → 需求日期 → 送審日期 → 發包日期 → 進場 → 驗收
```

### 三種表示，同一份資料

| 視圖 | 回答什麼問題 |
|---|---|
| **工序樹** | 依 WBS 分群，這個分類底下有哪些工序、誰是要徑、誰被 Gate 擋住 |
| **關聯表** | 逐道工序的完整十六欄，可匯出 Excel 交給工務或 ERP |
| **泳道圖** | 依施工單位（工種）分道的時間軸，一眼看出哪兩個工班在同一週撞在一起 |
| **材料需求日** | 從工序反推的採購日期鏈，以及「最早可行開工日」 |

### 每道工序的十六欄

`SequenceCode`｜`WBS`｜`工序名稱`｜`施工內容`｜`前置工序`｜`關聯FS/SS`｜`前置條件`｜`使用BOM`｜`施工單位`｜`介面工種`｜`檢查點`｜`是否隱蔽`｜`是否Gate`｜`後續工序`｜`來源圖號`｜`可信度`

「後續工序」是由前置關係**反算**出來的，不是另外維護的欄位 —— 兩邊各存一份必定會不一致。

### 十六類需要特別辨識的工序

送審、預埋、套管、開孔、基座、吊架、主管、支管、設備安裝、試壓、絕緣測試、單機測試、系統測試、聯動測試、隱蔽驗收、竣工驗收。

分類是關鍵字比對，但**比對順序有明訂優先級**（`KIND_PRIORITY`）。「套管預埋」同時命中「套管」與「預埋」，若照物件宣告順序比對會被泛用動詞「預埋」搶走；優先級把具體工項排在泛用動作之前。

### 關聯與浮時

- **FS**（Finish-to-Start）：前置完成後才能開始。
- **SS**（Start-to-Start）：前置開始後即可同步開始，常見於管線與支架同步施作。
- 兩者皆可帶 lag（**工作日**）。
- 正向排程算最早開始／完成，反向排程算最晚開始／完成，兩者之差為浮時，浮時為零者組成要徑。
- 拓撲排序用 Kahn 演算法，**迴圈相依會被偵測並明白回報**，不會讓程式空轉或吐出看似合理的假日期。

### Gate：核准節點

`IsGate = Yes/No`，`GateStatus = 未檢查 / Pass / Fail`。

Gate 的語意跟前置工序不同：**Gate 未通過會擋住所有下游工序，不管排程順序算出什麼**。隱蔽驗收、系統測試、竣工驗收預設都是 Gate —— 牆封了才發現沒驗，拆的成本遠高於等。

判定是**逐道 Gate、逐項下游**進行的：一道工序被三個 Gate 擋住，通過其中一個並不會讓它解封。

### 工作日與日曆日是不同的函式

`addWorkdays()` 與 `addDays()` 刻意分成兩個函式，不提供「自動判斷」的版本。

- **工期**走工作日（週末、行事曆假日不施工）。
- **採購反推鏈全部走日曆日**（工廠製造不會因為週末停擺，船期也不會）。

把兩者混用是這類工具最常見的錯誤，而且錯得很安靜 —— 日期看起來都很合理，只是全部偏早。

### 由工序反推採購日期

```
工序開始日 − 進場緩衝 (3d)     = 需求進場日
需求進場日 − 採購 Lead         = 最晚核准日
最晚核准日 − 送審天數 (14d)    = 最晚送審日 ＝ 建議發包日
建議發包日 − 內部核決 (7d)     = 建議 PR 日
```

**這個順序刻意跟一般 ERP 不同。** 台灣營建實務是先發包、廠商送審、**核准後才開始製造**，不是「下單即開始製造」。把 Lead 從下單起算，會讓所有日期早算掉一整個送審週期 —— 對 180 天前置期的冰水主機來說就是整整兩週的假餘裕。

工作例（範本資料，開工日 2026-09-14）：

| 氣冷式冰水主機 610.01 | 日期 |
|---|---|
| 工序開始（610-030 冰水主機安裝） | 2026-10-29 |
| 需求進場日（−3d 緩衝） | 2026-10-26 |
| 最晚核准日（−180d Lead） | 2026-04-29 |
| 最晚送審日／建議發包日（−14d） | 2026-04-15 |
| 建議 PR 日（−7d 內部核決） | 2026-04-08 |

同一材料被多道工序使用時，由**最早**需要它的那道決定 PR 日；晚的那道沒有話語權。

### 送審工序不是材料消耗點

送審工序會引用 BOM（為了追溯送的是哪一項），但它要的是型錄與試驗報告，**不是材料本身**。若把送審當成消耗點，會推出「送審那天材料就要進場」這種結論，把所有日期整整提前一個製造週期。

因此 `consumesMaterial()` 明確排除 `kind === 'submittal'`；只被送審工序引用、沒有任何安裝工序會消耗的材料，會列在 `orphans` 回報出來，**而不是硬算一個假日期**。推不出來就說推不出來。

### 最早可行開工日

反推鏈算完，範本資料 21 項材料全部「已逾期」—— 這是真的：以明天開工，180 天前置期的冰水主機在半年前就該發 PR 了。

但整片紅字回答的是「哪幾項遲了」，不是「那我最早能哪天開工」。`earliestFeasibleStart()` 拿最緊那條鏈的負浮時把開工日往後推，再用**真正的 `schedule()` 重跑**驗證，迭代到沒有任何一項負浮時為止。

不用線性外插，是因為工期走工作日：把工作日當日曆日外插，週末與國定假日會讓結果**偏早**，而偏早的答案比沒有答案更危險。收斂性上，開工日往後移不可能讓任何 ES 提前，浮時單調遞增，範本資料 1 次迭代即收斂（2026-09-14 → 2027-02-19，往後 158 天，卡在冰水主機）。

若迭代上限內收斂不了，工具會明說：那代表長前置期項目的 Lead 與工期本身矛盾，**要改的是採購策略，不是開工日**。

### 誠實規則：不得把工程慣例冒充圖說要求

這是整個模組最重要的一條規則。

工序範本產生的是**工程慣例**。每道工序都會拿去跟已載入的文件比對（`findEvidence`）：

- 找到證據 → 可信度升為「圖說」，並附上出處（檔名 + 行號 + 命中的關鍵字）。
- 找不到 → 一律維持「**建議工序／需工程確認**」，並在畫面上方明白標示有幾道。

Excel 匯出同樣帶這個標記。發包前請工程確認 —— 一個標成「圖說要求」但圖上其實沒有的工序，比沒有這道工序更危險。

## 四之四、原料行情連動

接 `/api/market-data`（銅／鋁／鋼／塑膠粒／匯率）。

這一節開頭先講這個模組**不做**的兩件事，因為那才是它跟同類工具的差別：

**一、不把行情價當成單價。**
「銅 13,700 美元，所以電纜多少錢」是錯的問法。一米 XLPE 電纜的單價裡，銅只佔一部分，
其餘是押出、被覆、運費、廠商毛利。正確做法是**物價指數調整式** —— 只讓原料部分隨行情浮動：

```
P_adj = P_base × ( a + Σ s_k × I_k / I_k0 )      a = 1 − Σ s_k
      = P_base × ( 1 + Σ s_k × (I_k/I_k0 − 1) )
```

這是 FIDIC Red Book 13.8（Adjustments for Changes in Cost）的結構，
也是台灣公共工程物價指數調整條款的結構。`a` 是不調整部分。

**二、不預測價格。** 沒有人知道銅價下個月往哪走，這個模組也沒有在猜。
它輸出的是**曝險**與**敏感度**：「往上走 10%，這批採購多付 NT$X」。
那是現在就能知道、而且能拿去談判的數字。

### 三個做錯就全盤皆錯的地方

| # | 陷阱 | 這裡怎麼處理 |
|:--:|---|---|
| 1 | **幣別** | 銅鋁 PP 報美元、鋼報台幣。指數一律換算成**台幣／公斤**再比。銅漲 10% 而台幣貶 5%，台幣成本是漲 **15.5%**，不是 10% —— 相加會少算。沒有匯率就回 `null`，不用預設值蒙混。 |
| 2 | **基準日** | 不知道 NT$780 是在哪個行情水準報的，就算不出調整額。沒有基準快照時調整額回 **0 並說明原因**，不靜默地拿今天的行情同時當基準與現值然後宣稱自己在跑即時行情。 |
| 3 | **指數對應** | SUS304 含鎳約 8%，價格由鎳與鉻主導，與鋼筋盤元脫鉤。行情表沒有鎳指數 → 標記 `none`，**不硬接一個相近的指數**。硬接只會產生看起來很精確的錯誤。 |

### 原料用量優先於宣告佔比

兩種設定方式，優先用前者：

- **`kg`** —— 每單位的原料用量。佔比由 `kg × 指數 / 基準單價` 推導。
  「1.0214 kg 銅/M」可以拿電纜規格書去對，「57%」不能。而且原料漲了，佔比會自動跟著變大。
- **`share`** —— 直接宣告佔比。只用於算不出用量的組裝品（盤體、主機）。

範本的 18 項連動設定，14 項是由物理量推出來的：

| 工項 | 依據 | 推出的佔比 |
|---|---|---:|
| 低壓電纜 3C×38mm² | 3 × 38mm² × 8.96 g/cm³ = 1.0214 kg/M | 銅 56.8% |
| 竹節鋼筋 SD420W | 指數標的本身，1 kg/KG | 鋼 80.0% |
| 消防配管 φ100 Sch40 | CNS 管重表 16.07 kg/M | 鋼 32.1% |
| PVC 排水管 φ100 A 級 | 2.4 kg/M | 塑膠粒 18.4% |
| 氣冷式冰水主機 250RT | 銅管 1,000 kg + 鋁鰭 300 kg + 鋼件 1,500 kg（概估） | 合計 11.8% |

電纜的 56.8% 與電纜業實務的 50–60% 相符，鋼筋的 80% 也與加工運費毛利佔兩成的常識相符 ——
這兩個獨立的交叉驗證是這套用量表站得住腳的理由。

### 連動品質分級

| 等級 | 意思 |
|---|---|
| **直接** | 指數標的就是該材料主成分（銅纜的銅、鋼筋的鋼），走勢可直接套用。 |
| **代理** | 相關但非同一材料（中鋼盤元代理鍍鋅鋼板），走勢部分重合，**幅度會失真**。 |
| **估計** | 原料用量為概估（冰水主機、配電盤），應以廠商自己的原料調整條款取代。 |
| **無指數** | 行情表沒有對應指數（不鏽鋼），**不連動**。 |

最弱的一條是 PVC 接 PP 指數：PVC 以乙烯與氯為原料，PP 以丙烯為原料，
兩者原料不同，僅同屬石化下游而有弱相關。程式裡明白標成 `proxy` 並寫出理由。

### 檢核：擋的是資料錯誤，不是行情異常

原料佔比必須落在 2%–100%：

- **超過 100%** → 單價低於原料成本。這不可能，是單價、用量或單位錯了。
- **低於 2% 且等級為直接／代理** → 材料本身就是產品，佔比不該這麼低，**單價的單位很可能錯了**。
- **低於 2% 且等級為估計** → 組裝品的價值不在原料，這是預期內的，不是錯誤。

這個檢核在範本上就抓到兩筆真實錯誤：`絕緣電線 5.5mm²` 填 NT$1,900、`Cat.6A 網路線` 填 NT$4,200。
銅含量推出的佔比分別只有 1.1% 與 0.2% —— 兩筆都是**整捲／整箱價填成每米價**。
5.5mm² 每米光是銅就值 NT$21.4，單價不可能是 NT$1,900 的同時只有 1% 是銅。
這種錯誤肉眼看不出來，發包前也不會有人發現，但會直接反映在估價金額上。

### 曝險用現在的原料價值算

原料漲了而加工運費毛利沒漲，原料佔比就變大了。沿用基準日的佔比會**低估曝險**，
而低估正是這個模組最不能犯的錯，所以曝險一律以現值計算：

```
原料曝險 = 採購量 × (kg × 目前指數)          用量設定
         = 採購量 × 宣告佔比 × 基準單價 × (目前指數 / 基準指數)    佔比設定
```

金額被拆成三塊，三者必須加總回總額：

| 分類 | 意思 |
|---|---|
| **可量測曝險** | 有對應指數，隨行情浮動。 |
| **量不出來** | 明確判定無指數的工項（不鏽鋼）。**曝險仍然存在，只是這張表量不出來** —— 併進「固定」會讓總曝險被低估。 |
| **加工／運費／毛利** | 真正不隨原料行情浮動的部分。 |

另外，被閘門鎖住、尚未定案的工項會**單獨列出**而不是悄悄消失：
它們的曝險是「還沒量到」，不是「沒有」。

### 鎖價窗口（接施工工序的反推日期）

發包當天價格就定了 —— 在那之後行情怎麼走都跟這一批無關。
所以「要不要現在鎖價」這個問題，**只有在窗口還開著的時候才存在**。
窗口的右界就是〈施工工序〉反推出來的**建議發包日**。

### 基準版必須連行情一起凍結

Baseline 凍結時會一併存下行情快照。否則原料指數天天在動，
對照基準版就會天天冒出「單價變了」的差異 —— 而其實沒有人改過任何東西。
幽靈差異會讓整個變更管理失去意義。

### 這張行情表有多少是真的即時

必須講清楚，因為它會影響金額：

| 項目 | 實況 |
|---|---|
| 匯率 USD/TWD | **每月自 API 抓取**（`open.er-api.com`，備援 `frankfurter.dev`，再備援固定值） |
| 銅／鋁／鋼／塑膠粒 | **人工維護的月更資料**（`public/data/market-source.json`） |

只有匯率是真正自動抓的。要真正即時，需接 LME／中鋼／台塑的授權資料源。
工具在畫面上直接標示這件事，不讓使用者以為四個指數都是即時的。

## 四之五、匯出：為什麼不是 CSV

### 問題有兩層，而且兩層都是安靜地壞

使用者按下匯出，畫面只跳出一句「此物品不提供文件下載」。拆開看是兩件不同的事：

**第一層：CSV 沒有編碼欄位。**
CSV 是純位元組，檔案裡沒有任何地方寫「我是 UTF-8」。Excel 只能拿系統碼頁去猜，
繁體中文 Windows 猜的是 Big5（CP950），於是 UTF-8 的中文整片變亂碼。
一般的解法是加 UTF-8 BOM，但那只是「大部分版本會認」——
Excel 的不同版本、不同地區設定、以及 Google 試算表與 LibreOffice 的行為並不一致，
有時 BOM 反而被當成第一格的資料。這條路本質上是在賭對方機器的設定。

**第二層：有些環境根本不讓網頁自己發起下載。**
把頁面嵌在別人的框裡（iframe、預覽器、部分企業入口）時，
`<a download>` 點下去不會有任何反應，也不會丟出例外 —— 使用者只看到「按了沒反應」。

### 做法

改成產生 `.xlsx`。`.xlsx` 內部是一個 ZIP，裡面是 XML，XML 的第一行就寫著
`encoding="UTF-8"` —— **編碼寫在檔案裡，沒有猜測的餘地。** 中文不會亂碼，
而且一個檔可以放多張工作表，不必把清單、採購包、工序拆成好幾個檔。

寫在 `public/js/takeoff/xlsx.js`，**零相依**：自己實作 CRC-32 與 ZIP 打包，
不引入 SheetJS 之類的函式庫。理由是這個工具處理的是投標圖說，
全部在瀏覽器端跑、不上傳；多帶一個第三方函式庫就是多一份要自己審的程式碼。

| 項目 | 做法 | 為什麼 |
|---|---|---|
| 儲存格型別 | 數字寫 `<v>`，文字寫 `inlineStr` | 數量存成文字就不能在 Excel 裡加總；反過來「321.01」這種工項代碼存成數字會變成 321.01 這個數 |
| 共用字串表 | 不用，一律 `inlineStr` | 少一個部件、少一處會對不起來的索引。代價是檔案略大，實務上的清單規模不痛 |
| 壓縮 | STORED（不壓縮） | 不必實作 deflate。三百列的清單大約 50 KB |
| 首列 | 凍結 + 粗體 | 三百列捲下去之後，不凍結就不知道哪一欄是哪一欄 |
| 欄寬 | 依內容估，中文算兩個字寬 | 不然中文欄一律被截成 `####` |
| 控制字元 | 除了 Tab/CR/LF 一律剝掉 | 一個 `0x07` 就能讓 Excel 拒開整份檔案。圖說文字裡真的會有 |
| 工作表名稱 | 砍到 31 字、去掉 `:\/?*[]`、重名加序號 | 這四件事任一條沒做，活頁簿就打不開 |

### 下載被擋的時候

匯出後對話框**會留著**，裡面同時給三條路：

1. 下載按鈕（再試一次，順便偵測是否真的被擋）；
2. **複製（可直接貼進 Excel）** —— 單張工作表時提供 TSV，
   用 Tab 分欄。貼上是走剪貼簿，**不經過任何檔案編碼猜測**，中文不會亂碼；
3. 一個可全選的文字框，連剪貼簿 API 都被擋時還能用 Ctrl+C。

偵測到頁面被嵌在別人的框裡時，會先用一段警語講明白「這個環境通常會擋掉下載，
按了可能沒反應，請改用複製貼上」—— 而不是讓使用者自己撞一次。

### 順手修掉的一個框架層的錯

對話框框架原本在按鈕的 `fn()` 執行完之後**無條件** `close()`。
若 `fn()` 自己開了一個新對話框，新的那個會被緊接著關掉 —— 畫面上就是「按了沒反應」。
這個錯在這個專案裡踩過三次（計算式表、單位換算補問、匯出）。
現在關閉帶世代號：內容已經被換成別的，這次關閉就作廢
（`dlgGen` / `dlgClose`，見 `app.js`）。這是框架層的修，不是在每個呼叫點補 `setTimeout`。

### 所有採購包 = 一個活頁簿

「所有採購包 RFQ」原本是一包下載一個檔。瀏覽器對連續多次下載本來就會擋，
而且採購真正要做的是「寄給不同廠商之前先自己整批核對」——
分成十個檔只會更難核。現在是一個活頁簿、一包一張工作表，工作表名用採購包代碼。

### 驗證

- `tests/xlsx.test.mjs`（25 項）自己解 ZIP、自己驗 XML 結構，不靠任何套件 ——
  匯出這條路的重點就是零相依，驗證端若靠第三方解析器，等於把最該驗的那段外包出去。
  涵蓋 CRC-32 標準測試向量、`Z→AA` 進位、型別、跳脫、控制字元、
  不等長的列、`NaN/Infinity`、5000 列、工作表重名。
- `tests/e2e.mjs`〈7之四〉實際開瀏覽器按匯出，驗證對話框不會被關掉、
  活頁簿列數與工項數相符、TSV 後備的欄數與活頁簿一致、多包匯成多工作表且名稱不重複。

## 四之六、換圖與清除：「更新圖面」為什麼不只是再載入一次

### 使用者問的是「沒有清除鍵」，實際問題比那更糟

原本的行為是：按「載入圖面」確實會換掉畫面上的圖。所以嚴格說，圖**更新得了**。
但更新得不乾淨，而且不乾淨的地方一個字都不講：

| 換圖後留下來的 | 後果 |
|---|---|
| 上一張圖的**量測** | 座標屬於舊圖，畫在新圖上位置完全不對，還會用新圖的比例去換算舊圖的原始長度 —— **算出一個看起來正常的假數字** |
| 上一版圖寫進清單的**圖面量** | 數字還在、出處欄還寫著舊檔名，畫面上沒有任何提示 |
| `notToScale` 旗標 | 上一張標 NO SCALE 的圖，會讓下一張正常的圖也永遠量不出工程單位 |
| DXF 的**計算式晶片** | 換成 PDF 之後還掛在工具列上，指向一張已經不在畫面上的圖 |

前兩項是靜默的錯誤數字，後兩項是靜默的功能失效。**四項都不會報錯。**

### 三個設計判斷

**一、量測依圖分開存，不是換圖就刪掉。**
量測的座標只在畫它的那張圖上有意義。但直接刪掉會讓「切出去看一下別張圖再切回來」
變成懲罰。所以用 `measureKey = 圖名@簽章#頁次` 分組：換圖時把現有的收起來、把該圖的拿出來。
切回同一張圖，量測就回來了。PDF 換頁同理 —— 第 1 頁畫的線在第 2 頁上不該出現。

**二、`qty.drawing` 絕對不自動清除。**
這是最重要的一個判斷。那些數字可能已經被人看過、已經進了基準版、已經發包。
在使用者不知情的情況下自動刪掉，**比留著更危險**。
工具的職責是讓它**變得看得見**，不是替使用者決定：標成「舊版」，跳一次對話框攤開受影響的工項，
然後把清或留交回去。

**三、判斷「過期」的訊號是「同名不同內容」，不是「跟目前載入的圖不同」。**
一個案子本來就有電氣圖、給排水圖、空調圖好幾張。
如果用「目前載的圖 ≠ 數量的出處圖」去判定過期，載一張給排水圖就會讓所有電氣的量整片標成過期 ——
**誤報的警告比沒有警告更糟，因為人會學會忽略它。**
唯一可靠的訊號是：同一個檔名，內容變了 = 這張圖改版了。

簽章用檔案頭尾各 64KB 加檔案大小做 FNV-1a。不是為了防竄改，所以不需要密碼學雜湊；
全檔雜湊對 50MB 的 DWG 會卡住畫面，那個代價換不到對應的準確度。

### 清除是分層的，不是一顆核彈

標題列的「清除／更新圖面」開出四個動作，每一個都標明會影響幾筆：

| 動作 | 影響 | 不影響 |
|---|---|---|
| 清除本圖量測 | 這張圖這一頁的量測 | 已寫進工項的圖面量、其他圖的量測 |
| 清除標成「舊版」的圖面量 | 改版後留下的舊數字 | BOQ 量、人工確認量、計算式量 |
| 清除本圖產生的所有圖面量 | 出處是這張圖的圖面量，不分新舊 | 同上 |
| 卸載圖面 | 畫面回到未載入 | 量測依圖保存著，重載同一張圖就回來 |

「參數」裡的「重置為範本」是另一回事 —— **那一顆會連採購包、基準版、已產生的請購單一起清掉，
且無法復原**，說明文字現在把這件事講明白了。

### 順手修掉的一個 CSS 錯誤

`.chip{display:inline-flex}` 會蓋掉瀏覽器預設的 `[hidden]{display:none}`，
所以 `#calcChip` 和 `#pageChip` 設了 `hidden` 卻還是看得見 ——
工具列上一直掛著兩個空的小膠囊。

**這個錯只在自架時看得到**：Artifact 的外框會自己注入 `[hidden]{display:none!important}`，
所以展示版正常、自己架起來就有兩顆空膠囊。現在 `takeoff.html` 自己也寫了這條規則。

### 驗證

`tests/e2e.mjs`〈7之五〉實際開瀏覽器換圖：量測歸屬鍵、換圖後舊量測不殘留、
切回同一張圖量測會回來、**換到別張圖不誤報過期**、同名不同內容判定為改版並列出受影響工項、
清單顯示「舊版」標記、標成舊版不等於自動刪除、清除只清該清的、卸載後晶片一起收掉。

## 五、這個工具刻意不做的事

- 不取代 BIM 模型算量（IFC `IfcElementQuantity` 才是可追溯的數量單一真實來源）。
- 不做鋼筋翻樣、不自動判讀掃描圖上的文字標註。
- 不宣稱量測結果可直接作為契約數量。它做的是把三條線攤開比對，讓每一筆採購量都有出處。

## 七、全球頂尖專家對這類工具一致會質疑的五件事

**1. 「單一真實來源」的謬誤 —— 2D 圖面算量本質上不可追溯。**
BIM／IFC 之所以被推，是因為數量掛在物件上，改模型數量自己動。2D 圖面量測是**一次性快照**：
圖一改版，你量的東西就過期，而且沒有任何機制告訴你它過期了。本工具用「數量出處 + 時間戳 + 圖名頁碼」
把快照釘住，但那只是把問題變成可見，不是解決。專家會問：**你的版本控制在哪裡？**
可行的補強是引入圖號版次欄位並在圖面更新時把相關工項標記為 stale。

**2. 單一損耗率係數在統計上站不住腳。**（**已處理**，見〈損耗率機率化〉）
3% 是慣例不是證據。專家會問：**你的 P50 和 P80 差多少？**
現在答得出來：電纜 P50 = 1,759.7 M、P80 = 1,777.1 M，而慣用的 3% 只相當於 **P30**。
整包層級也答得出來，並且處理了相關性與加總謬誤這兩個最容易算錯的地方。
**尚未解決的部分**：區間本身仍是慣例值。要真正站得住腳，需要貴司自己的實績資料校準 ——
工具已備好校準入口，但沒有資料它就只是把慣例值包裝得比較好看而已。

**3. 差異的合約意涵，比差異本身重要得多。**
圖面量 1,710 對上 BOQ 量 1,650，在 **remeasurement（實作實算）** 合約下是估驗計價的依據調整；
在 **lump sum（總價承攬）** 合約下卻可能是承包商自己吸收的成本，或反過來是變更設計索賠的證據。
把它當成「取 1,700 折衷」處理，是把一個合約問題偽裝成算術問題。
**專家會問：這個 1,700 是誰簽的、依據哪一條契約條款、有沒有進變更設計程序？**
本工具強制人工確認要填簽核人與理由，就是為了讓這一題至少有答案 —— 但工具管不了流程，你得管。

**4. CPM 的確定性工期假設，跟機率化損耗率是同一個毛病。**
工序表給每道工序一個確定的天數，然後算出一條要徑與一組浮時。但工期本身是隨機變數 ——
而且 Merge Bias（多條路徑匯流時，完成日的期望值一定晚於各路徑期望值的最大者）會讓
確定性 CPM **系統性低估**專案工期，這是 PERT 自 1958 年就已知的結構性缺陷。
專家會問：**你的要徑在 P80 下還是同一條嗎？**
現在答不出來。損耗率已經機率化了，工期還沒有 —— 這是不一致的。
正確做法是把工期也丟進同一套 Monte Carlo（`risk.js` 的機器已經在了），
輸出各路徑成為要徑的機率（criticality index），而不是一條看起來很確定的紅線。
在那之前，工序表上的日期請當作**中位數情境**看待，不是承諾。
參考：Vanhoucke, *Measuring Time: Improving Project Performance Using Earned Value Management* (Springer, 2010)；
AACE **RP 57R-09**（Integrated Cost and Schedule Risk Analysis）。

**5. 指數本身的品質，比連動公式重要得多。**
公式再對，餵進去的是每月人工維護的靜態檔，答案就只有每月的解析度。
真正的痛點在**計價期（pricing period）**：LME 銅的合約通常以「下單前一個月的月均價」或
「交貨前一個月的月均價」計價，不是下單當天的現貨價。本工具目前用的是單點現貨價，
跟廠商實際結算的基準**不一致**，差異在波動期可達數個百分點。
專家會問：**你的指數計價期跟供應商合約的計價期對得上嗎？**
現在對不上。要對上，需要（a）月均價序列而非單點，（b）每個供應商的計價期設定。
在那之前，連動金額是**方向正確、幅度近似**，可以拿來談判，不能拿來結算。
另外不鏽鋼那 2.4% 的「量不出來」也是同一個問題的一部分 —— 缺的是鎳指數與合金附加費機制。
參考：LME **Rulebook**（Settlement Price）；ISSF 合金附加費說明。
