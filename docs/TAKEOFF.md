# WBS 階層式工程量清單選擇器

`/takeoff.html` — 讀圖 → 量測 → 多來源比對 → 建議採購量 → 轉採購 Package 的一條龍工具。
全部在瀏覽器端執行，圖面不上傳（除非你自己設定了 DWG 轉檔服務）。

```
public/takeoff.html            頁面與樣式
public/js/takeoff/quantity.js  基準判定、可信度、損耗、建議採購量、自動拆包（純函式）
public/js/takeoff/analysis.js  圖說解析規則引擎：規格屬性、六類 RFI、狀態流、九項指標（純函式）
public/js/takeoff/baseline.js  基準版凍結、變更對照、PR 編號與 ERP 欄位對映（純函式）
```

## 〇、解析中心（進入點）

對應流程圖的前半段：**AI 圖說解析 → 圖說 / 規範 BOQ → WBS → 規格 + QTO → 差異 / 特殊規格 → RFI**。

1. 填專案名稱、選合約型態。
2. 上傳四類文件：**圖說 / 規範 / BOQ / 設備表**。圖說可再標記平面圖／系統圖／詳圖／表單（由檔名預猜）。
3. 勾選分析範圍（全工程或指定大類）。
4. 按「開始解析」，得到九項指標、流程階段列與 RFI 候選清單。

### 九項指標怎麼算出來的

| 指標 | 定義 |
|---|---|
| 圖說完整性 | 五項可查證比例的加權，見下 |
| WBS | 範圍內有工項的分類節點數 |
| 工項 | 範圍內工項數 |
| 材料／設備 | 扣掉「式」計價的統包項 |
| 數量已確認 | 基準判定狀態為 ok（非需複核、非鎖定） |
| 特殊規格 | 工項標記 `special`（無法用標準品替代） |
| 差異 | 圖面量與 BOQ 量差異超過容忍門檻的項數 |
| RFI 未結案 | 候選＋已發出＋已回覆的總數（逾期另計並標紅） |
| 長交期 | 前置期 ≥ `longLeadDays`（預設 90 天） |

**圖說完整性不是 AI 打的分數**，是五個比例的加權，點開可逐項攤開：

| 項目 | 權重 |
|---|--:|
| 工項有數量來源（圖面量或 BOQ 量） | 30% |
| 工項已連結圖面（量測或圖層彙總） | 25% |
| 規格完整（材質／尺寸／等級／標準） | 25% |
| 圖面已設定比例 | 10% |
| 無未解 RFI | 10% |

要拉高它只有一條路：補文件、補規格、設比例、結案 RFI。換演算法不會讓它變好看。
沒有工項時直接回 0 —— 不靠「沒有 RFI」湊分數。

### 六類 RFI 偵測規則

| 類型 | 觸發條件 | 證據 |
|---|---|---|
| 圖說 ≠ BOQ | 差異率超過容忍門檻 | 兩邊數量、差異率、數量出處 |
| 圖說 ≠ 規範 | 工項規格與規範文件同一行的材質／等級 token 無交集 | 規範原文與行號 |
| 平面圖 ≠ 系統圖 | 同一設備標籤在兩類圖的實例數不同 | 各自的標籤清單 |
| 設備表 ≠ 詳圖 | 標籤只出現在設備表或只出現在圖面 | 兩邊出現次數 |
| 數量無法判斷 | 無任何數量來源／未連結圖面／面積取自未封閉輪廓 | 各來源狀態與原因 |
| 規格不完整 | 缺少該類工項的必要規格屬性 | 現有規格與缺少項目 |

兩個刻意的設計，都是為了**不製造假 RFI**（假 RFI 比沒有 RFI 更糟，它讓人開始忽略整張清單）：

- **泛稱不參與衝突判定**。「不鏽鋼」兩邊都會出現，拿它比對會把 `SUS304 vs SUS316` 的真衝突洗掉；
  反過來拿模糊詞宣稱衝突則會製造假案。所以另立一組高特異性 token（SUS3xx、Sch__、IP__、SD___…）。
- **必要規格屬性依工項性質而定**。混凝土的規格就是強度（`f'c=280`），要它填「材質、尺寸」只會生出假 RFI；
  鋼筋要的是等級＋號數＋標準。工項可用 `requiredSpec` 覆寫。

### RFI 狀態流

偵測出來的只是「候選」。要成為閉環，它得走完一整條狀態鏈：

```
候選 ──發出──→ 已發出 ──登記回覆──→ 已回覆 ──結案──→ 已結案
  │                │                              ↑
  └──不追（必填理由）─┴──────────直接結案────────────┘
                                   已結案／不追 ──重開──→ 回到前一狀態
```

三個刻意的設計，少了任何一個這功能就是裝飾品：

**1. 文號在「發出」時才配並凍結。**
偵測階段不給文號 —— 沒發出去的東西不該有正式文號。因為 RFI 是每次重算產生的，
若依排序編號，重算一次順序變了，你已經發文出去的 `RFI-003` 就會變成別人。
發出時才配號、並把**問題內容快照凍結**：之後就算重新解析、條件改變，
你發文問的那句話都不會被悄悄改寫。

**2. 已發出的 RFI 即使條件消失也保留。**
設計單位改了圖，下次偵測就抓不到那筆不一致 —— 但公文已經發出去了。
系統會保留該筆並標記「**條件已消失**」，提醒你確認後結案，而不是靜默刪掉一筆已發出的公文。
候選則相反：條件消失就消失，不留垃圾。

**3. 未結案的 RFI 會擋住該工項轉採購。**
預設擋「高嚴重度」（參數可調為「中以上」或「不擋」）。閘門以**工項**為單位：
同一工項上還有其他未結案的高嚴重度 RFI 就不放行。出路是把它發出並結案，
或填理由「不追」—— 這個摩擦是刻意的，等於強迫你對每一筆問題做出決定。

**結案動作就是閉環本身**：

| 動作 | 效果 |
|---|---|
| 採用回覆數量 | 寫入工項的**人工確認**，簽核人記為回覆人、理由記為 RFI 文號＋回覆原文 |
| 採用回覆規格 | 更新工項規格 |
| 無需變更 | 只留紀錄 |

登記回覆時要求**原文照抄**：結案若採用回覆數量，那段文字會成為工項上的「確認理由」，
是日後估驗與爭議時的依據。改寫過的回覆沒有證據力。

每筆 RFI 都有完整歷程（誰、什麼時候、從什麼狀態到什麼狀態、附註），匯出 CSV 含
狀態／公文文號／發出日／期限／逾期／回覆內容／回覆人／結案動作／不追理由／條件是否仍存在。

### 這裡的「AI」在哪裡

目前沒有。九項指標與每一筆 RFI 都由**明文規則**從已載入文件的實際內容算出，每一條都附證據
（哪份文件、第幾行、哪個數字），可重現、可稽核。
日後若接上語言模型做語意比對，應該把它當成**第二意見**寫進 evidence，而不是取代這些規則 ——
稽核要的是可重現，不是看起來很聰明。

## 二、數量從哪來（這是整個工具的重點）

五種來源，其中只有三種算「獨立量測」：

| 來源 | 獨立 | 基礎分 | 說明 |
|---|:--:|--:|---|
| 人工確認 | ✕ | 88 | 對其他來源做的判斷，不是新的觀測 |
| 圖面量 | ✓ | 78 | 量測或圖層彙總 |
| BOQ 量 | ✓ | 70 | 契約／標單數量 |
| 供應商量 | ✓ | 66 | 廠商回覆 |
| 歷史類比 | ✕ | 52 | 外插，僅供參考 |

**人工確認與歷史類比不納入一致性計算。** 把人工填的數字算進「三來源高度一致」，
等於拿自己的答案幫自己背書（circular corroboration），會讓信心分數系統性灌水。

### 基準判定規則（明文、可重現）

```
R1  有人工確認            → 採人工確認（必須有簽核人與理由）
R2  圖面量與 BOQ 量都有：
      |差異率| ≤ 5%        → 採圖面量，狀態 ok
      5% < |差異率| ≤ 10%  → 採圖面量，狀態「需複核」
      |差異率| > 10%       → 鎖定，不產生建議採購量，強制人工確認
R3  其餘                  → 依 人工 > 圖面 > BOQ > 供應商 > 歷史 取第一個有值者
```

差異率分母是 **BOQ 量**（契約基準），不是兩者平均 —— 你要回答的問題是
「相對於標單，圖面多了多少」，不是「兩個數字差多少」。

手動指定基準時，若差異仍超上限，狀態一樣維持「需複核」；覆寫不能靜默繞過閘門。

### 可信度評分

`基礎分 + min(正分總和, +12) + 負分總和`，夾在 0–100，分級 A ≥85 / B ≥70 / C ≥55 / D <55。

正分封頂、負分不封底，是刻意的：**信心不可能高過來源本身的上限，但證據缺陷可以把它打到地板。**
若不封頂，好項目全部飽和在 100，分數就失去鑑別力。

扣分項包括：PDF 未校正（−20）、校正殘差 >2%（−6）、來源嚴重落差（−22）、
未封閉輪廓求面積（−15）、圖層模糊比對（−5）、圖面涵蓋不完整（−8）、
人工確認無理由（−8）、人工值落在量測區間外（−10 ~ −18）。

點表格上的等級徽章可以攤開每一分的來源。**這是可稽核的啟發式評分，不是統計信賴區間**，
UI 上也是這樣寫的 —— 它回答「證據鏈完不完整」，不保證誤差落在某個範圍。

### 建議採購量

```
建議採購量 = 基準量 × (1 + 損耗率)                    ← 對應人工報表的那一行
下單量     = ceil(建議採購量 ÷ 每訂購單位含量, 包裝倍數)，再套 MOQ
到貨量     = 下單量 × 每訂購單位含量
```

例：基準 1,700 M、損耗 3% → 建議 **1,751 M**；若改成 6 M/支，下單 292 支、到貨 1,752 M。
`ceilTo()` 用相對誤差吸收浮點雜訊，避免 `1700 × 1.03 = 1751.0000000000002` 被多進位一階。

## 三、圖面怎麼讀

### DXF（原生支援）

自寫的 ASCII DXF 解析器，支援 LINE / LWPOLYLINE（含 bulge 弧）/ POLYLINE+VERTEX /
CIRCLE / ARC / ELLIPSE / SOLID / 3DFACE / TEXT / MTEXT / INSERT（圖塊遞迴展開、含矩形陣列）/ DIMENSION。

- bulge 弧長：`θ = 4·atan(|b|)`，`R = c / (2·sin(θ/2))`，`L = R·θ`；面積另加弓形修正。
- 單位取 `$INSUNITS`；未定義時強制使用者指定，不猜。
- SPLINE 以控制點折線近似（長度為下界並標記），HATCH 只計數不算面積 —— 寧可少算也不要假裝算得出來。
- 圖層彙總（總長／總面積／實體數／圖塊數）可一鍵對映到工項，靠 `layerHints` 自動猜。

### PDF（原生支援）

pdf.js 渲染 + 像素邊緣吸附（向量與掃描件都適用）。**未校正比例前不顯示任何工程單位。**

- 兩點校正：點兩點已知尺寸、輸入實際長度。
- 多段校正：累積 2 段以上改用最小平方求比例，回報 **RMS 殘差** —— 這是「這份圖量得準不準」的客觀證據，直接餵進可信度。
- 圖框比例（1:N）：`metersPerPt = (0.0254/72) × N`。此法假設 PDF 由 CAD 以 1:1 圖紙尺寸輸出且列印未縮放，
  實務常見「A1 縮印 A3」而失真，所以評分上扣分。

### WBS 編碼

採貴司自有的九大類：

```
100 土建   200 裝修   300 電氣   400 給排水   500 消防
600 空調   700 弱電   800 設備   900 其他
```

三層結構：**大類（3 位）→ 中類（3 位）→ 小類（3 位，選用）→ 工項**。例如
`300 電氣 → 320 幹線 → 321 電纜 → 321.01 低壓電力電纜 XLPE`。
範本在 `public/data/wbs-template.json`，直接改成貴司標準即可，程式不綁任何特定編碼。

### DWG（需轉檔，這是硬限制）

DWG 是 Autodesk 的封閉二進位格式。本專案**不內嵌任何 DWG 解析器**，原因是授權而非技術：
唯一可靠的自由實作 GNU LibreDWG 是 **GPL-3**，把它連結進網站程式會讓整份程式落入 GPL-3 散布義務。
改成呼叫獨立行程／獨立服務則不會。

**選項 A（採用中）：自建轉檔服務，圖面不出公司**

本專案已附上可直接跑的實作：`tools/dwg-converter/`（零相依 Node 服務 + Dockerfile + 測試）。

```bash
docker build -t dwg-converter tools/dwg-converter
docker run -d -p 8787:8787 -e TOKEN=your-secret dwg-converter
# 網站端：DWG_CONVERT_URL=http://<內網位址>:8787  DWG_CONVERT_TOKEN=your-secret
```

轉檔器解析順序：`DWG_CONVERT_CMD` → `ODAFileConverter` → `dwg2dxf`。細節見該目錄的 README。


```bash
# ODA File Converter（Open Design Alliance 免費工具，品質最穩）
ODAFileConverter /in /out ACAD2018 DXF 0 1 "*.dwg"

# 或 LibreDWG（GPL-3，命令列獨立行程）
dwg2dxf -o out.dxf in.dwg
```

把它包成一支 HTTP 服務，契約很單純：

```
POST /                       ← DWG_CONVERT_URL 指向這裡
Content-Type: application/octet-stream
X-Filename: <URL 編碼的原始檔名>
Body: DWG 原始位元組

200 OK
Content-Type: application/dxf
Body: ASCII DXF 文字（必須以 `0 / SECTION` 開頭）
```

然後設定：

| 環境變數 | 用途 |
|---|---|
| `DWG_CONVERT_URL` | 轉檔服務端點（未設定時 `/api/convert-dwg` 回 501 並附指引） |
| `DWG_CONVERT_TOKEN` | 選用，帶 Bearer 認證 |
| `DWG_CONVERT_TIMEOUT_MS` | 預設 120000 |
| `DWG_MAX_BYTES` | 預設 40 MB |

`/api/convert-dwg` 會驗證回應確實是 ASCII DXF（開頭必須是 `0 / SECTION`），不是就回 502，
不讓前端拿垃圾去硬解析。

**選項 B：瀏覽器端 GPL WASM（自負授權責任）**

頁面載入前設定 `window.TAKEOFF_LIBREDWG_BASE = 'https://…/libredwg-web/'`，
會動態載入 `@mlightcad/libredwg-web`（GPL-3、WASM 約 10 MB）並用 `dxf.js` 的 `fromDwgDatabase()` 轉成內部模型。
**本專案不散布這份程式碼**，開關預設關閉，商用前請先做授權合規判斷。

**選項 C：人工轉出** — 另存 ASCII DXF 或列印向量 PDF。功能完全相同，五秒的事。

## 四、轉採購 Package

- 未達可信度門檻（預設 C）或狀態鎖定的項目**不會**被納入包，並在對話框逐項列出原因。
- 需求到貨日預設 = 今天 + 最長前置期 + 7 天緩衝。
- RFQ CSV 含 UTF-8 BOM，Excel 直接開。保留 `判定規則 / 簽核人 / 確認理由 / 數量出處` 四欄 ——
  稽核時真正會被問的就是這四欄。

前置期是拆包的關鍵：把 120 天的配電盤和 14 天的 PVC 管綁在同一包，
等於讓整包被最慢的品項綁架。工具會顯示每包的最長前置期，讓這件事無所遁形。

## 四之二、基準版（Baseline）與請購單（PR）

對應流程圖末段：**採購需求/Package → 工程確認 → Baseline/PR → 正式發包**。

### 凍結

採購包按「凍結為基準版」，把當下每個工項的採購狀態壓成快照：
規格、單位、採購基準、基準量、損耗率、建議採購量、下單量、到貨量、單價、金額、可信度、前置期。

**必須填工程確認人** —— 沒人確認的快照不是基準版，只是一份沒人負責的檔案。
這一欄就是流程圖上 Package 與 Baseline 之間的那一關。

重新凍結產生新版（rev 2、rev 3…），每版記錄誰確認、何時、為什麼，並指向前一版。

### 凍結不等於鎖住

**Baseline 的用途不是禁止改動，而是讓「改了什麼、誰改的、差多少錢」無所遁形。**
凍結後資料照樣能改，但每一項異動都會被對照出來：

- 基準版卡片顯示「較本基準版有 N 項異動…金額差 X」
- 工程量清單上，異動過的工項下方直接標出 `較 BL-PKG-001-01 異動：基準量 +60、建議採購量 +61.80…`
- 點「變更」看完整對照表：每個欄位的基準版值、現值、差異

浮點雜訊（`1751` vs `1751.0000000000002`）不會被當成變更 —— 相對誤差 1e-9 內視為相同。

### 請購單編號

樣板可設定，預設 `PR-{YYYY}{MM}{DD}{SEQ:4}` → **PR-202609130001**。
可用 token：`{YYYY} {YY} {MM} {DD} {SEQ:n}`。

**流水號的重置範圍由樣板自動推導**：有 `{DD}` 就每日重置、只有 `{MM}` 就每月重置、
只有 `{YYYY}` 就每年重置。這是為了避免「編碼精確到日、流水號卻全年連續」這種自相矛盾
（也可明確覆寫）。其他區間的舊號不會干擾本區間的取號。

### 單價換算

PR 明細的單價是以**訂購單位**計價，不是材料單位。
6 M/支的管子，單價寫的是「每支」= 每公尺 × 6 —— 否則 ERP 那邊金額會差六倍。

### 進 ERP

本工具**不綁任何一套 ERP**：中性資料模型 + 可設定的欄位對映。

| 項目 | 說明 |
|---|---|
| 結構 | 表頭 + 明細兩層，對應多數 ERP 的請購單 |
| 檔案格式 | 兩檔式（header.csv + detail.csv，明細帶單號可對回表頭）或單檔式（表頭欄位攤進每一列） |
| 欄位對映 | 把對方 ERP 匯入範本的欄名（`PURCH_NO`、`ITEM_NO`…）填進對映表，匯出的 CSV 表頭就用那個名字 |
| 料號把關 | 缺 ERP 料號的項目**先擋下來**並提供就地補填 —— 沒有料號送進 ERP 一定退件，不該等到 ERP 前台才發現 |

## 七、全球頂尖專家對這類工具一致會質疑的三件事

**1. 「單一真實來源」的謬誤 —— 2D 圖面算量本質上不可追溯。**
BIM／IFC 之所以被推，是因為數量掛在物件上，改模型數量自己動。2D 圖面量測是**一次性快照**：
圖一改版，你量的東西就過期，而且沒有任何機制告訴你它過期了。本工具用「數量出處 + 時間戳 + 圖名頁碼」
把快照釘住，但那只是把問題變成可見，不是解決。專家會問：**你的版本控制在哪裡？**
可行的補強是引入圖號版次欄位並在圖面更新時把相關工項標記為 stale。

**2. 單一損耗率係數在統計上站不住腳。**
3% 是慣例不是證據。實際損耗隨材料、幾何複雜度、施工方法、工班素質而變，
WRAP 的數據顯示同一材料的浪費率跨案場可差數倍。單點值等於把一個機率分布壓成一個數字，
然後假裝它沒有變異。**專家會問：你的 P50 和 P80 差多少？** 正確做法是對損耗率給區間並跑蒙地卡羅，
輸出「95% 信心下不缺料的採購量」，而不是一個看起來很精確的 1,751。

**3. 差異的合約意涵，比差異本身重要得多。**
圖面量 1,710 對上 BOQ 量 1,650，在 **remeasurement（實作實算）** 合約下是估驗計價的依據調整；
在 **lump sum（總價承攬）** 合約下卻可能是承包商自己吸收的成本，或反過來是變更設計索賠的證據。
把它當成「取 1,700 折衷」處理，是把一個合約問題偽裝成算術問題。
**專家會問：這個 1,700 是誰簽的、依據哪一條契約條款、有沒有進變更設計程序？**
本工具強制人工確認要填簽核人與理由，就是為了讓這一題至少有答案 —— 但工具管不了流程，你得管。
