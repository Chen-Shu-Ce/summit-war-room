1. 系統架構總覽

設計原則：先以單體服務（Monolith）部署，模組化設計內部邊界。等流量和團隊規模需要時，再拆成微服務。11~20 人規模不需要一開始就做分散式。

2. 採購流程線

四軌流程（16 步驟）：工程端①得標立項 → ②分包計畫 → ③工程預算 → ⑤送審 → ⑥需求單 SR → 採購端⑦文件審核 → ⑧詢比議價 → ⑨採購申請 PR → ⑩核決發包 PO → 竣工端⑭竣工檢查 → 驗收 → ⑮請款 → ⑯結案 → 財務端付款週期、實付、帳務沖銷。各端透過 source_id 串連，狀態推進獨立。
④採發會議（金額 ≥ 100 萬）與⑪~⑬施工管理為現場作業步驟，系統以日報、進度表、變更單支援，不在主流程線上。

3. 資料模型

3.1 共用基底欄位（Base Entity）

所有單據共用同一組基底欄位，確保一致的稽核軌跡與併發控制：

{
  "id":               "uuid",        // 主鍵
  "source_id":        "uuid | null", // 來源單據（SR→PR→PO 的串連）
  "legal_entity_id":  "uuid",        // 法人實體
  "project_id":       "uuid",        // 所屬專案
  "wbs_id":           "uuid | null", // 工作分解結構
  "row_version":      "integer",     // 樂觀鎖版本號（每次更新 +1）
  "created_by":       "uuid",        // 建立者
  "updated_by":       "uuid",        // 最後修改者
  "created_at":       "timestamptz", // 建立時間
  "updated_at":       "timestamptz", // 最後修改時間
  "status":           "varchar(32)", // 狀態（各單據不同）
  "idempotency_key":  "uuid"         // 冪等鍵（防重複送出）
}

5. 樂觀鎖與併發控制

5.1 機制

Optimistic Concurrency Control（OCC）

每張單據帶一個 row_version（整數）。每次成功寫入時 +1。更新請求必須帶上客戶端手上的版本號；後端比對，不符即拒絕。

5.2 完整流程

// 1. A 開啟 PR-001
GET /api/v1/purchase-requests/PR-001
→ { ..., "row_version": 7 }

// 2. B 也開啟同一張
GET /api/v1/purchase-requests/PR-001
→ { ..., "row_version": 7 }

// 3. A 先存
PUT /api/v1/purchase-requests/PR-001
{ ..., "row_version": 7 }                // ← 帶上手上的版本
→ 200 OK { ..., "row_version": 8 }       // ← 後端 +1

// 4. B 再存（帶的還是 7）
PUT /api/v1/purchase-requests/PR-001
{ ..., "row_version": 7 }                // ← 過時了
→ 409 Conflict
{
  "error": "CONFLICT",
  "message": "此單據已被其他使用者修改，請重新載入",
  "current_version": 8,
  "updated_by": "A 的名字",
  "updated_at": "2026-11-22T10:30:00Z"
}

5.3 後端 SQL

UPDATE purchase_requests
SET    data = $new_data,
       row_version = row_version + 1,
       updated_by  = $user_id,
       updated_at  = now()
WHERE  id = $id
AND    row_version = $client_version;   -- 關鍵：版本比對

-- affected_rows = 0 → 409 Conflict

5.4 前端處理

async function save(doc) {
  const res = await fetch(`/api/v1/${doc.type}/${doc.id}`, {
    method: 'PUT',
    headers: {
      'Content-Type': 'application/json',
      'Idempotency-Key': doc.idempotencyKey
    },
    body: JSON.stringify(doc)
  });

  if (res.status === 409) {
    const conflict = await res.json();
    // 顯示衝突對話框，讓使用者選擇：
    // 「重新載入」或「覆蓋（強制寫入）」
    showConflictDialog(conflict);
    return;
  }

  const saved = await res.json();
  doc.row_version = saved.row_version;  // 更新本地版本
}
冪等鍵（Idempotency-Key）：前端在建立新單據時生成一組 UUID 放進 header。若網路中斷重送，後端看到相同的 key 會回傳同一筆結果，不會建出兩張一樣的單。

6. 單據狀態機

6.1 通用狀態流（適用 SR / PR / PO）

6.2 各單據特有狀態

單據額外狀態說明
SR 需求單CONVERTED已轉成 PR，不可再修改
PR 採購申請QUOTING詢比議價中
PO 發包單EXECUTING COMPLETED履約中 / 已完工
驗收PARTIAL COMPLETED部分驗收 / 全部驗收完成
請款PAID已付款（V3.1 付款週期）

6.3 單號編碼規則

承辦建立單據時須先選擇所屬法人實體，系統依法人前綴自動產生單號：

法人實體前綴編碼格式範例
森陽SYSY-YYMM-NNNSY-2611-001
春合CCCC-YYMM-NNNCC-2611-001
涌全YQYQ-YYMM-NNNYQ-2611-001

YYMM 為民國年月；NNN 為當月流水編號，每月重算自 001 起。適用所有單據類型（SR、PR、PO、驗收、請款）。

8. 測試場景

#場景分類驗證重點
1工程同時新增需求併發兩個工地主任同時建 SR，各自成功、ID 不重複
2工地主任簽核流程SR 送審 → 工程主管核准 → 狀態正確推進
3採購承辦轉 PR轉單SR → PR，source_id 正確串連、附件自動帶過
4採購主管簽核流程PR 核准、退回、重送完整流程
5附件權限權限只有相關角色能下載/刪除附件
6同一單據多人修改衝突併發row_version 衝突 → 409、訊息正確
7標單外需求業務不在原始標單內的需求，預算勾稽應警告
8超採購預算業務PR 金額超過採購預算時，提醒但不擋（主管可覆核）
9重複需求業務idempotency_key 防止同一張 SR 建兩次
10V3.1 付款週期財務請款 → 付款日計算（銀行行事曆、會計期間）
